100Overview

For anyone. One page.

Tradecraft is a program that runs on the user's own computer and is used through a web browser. The user types one underlying; the program takes it through four stages and stops for the user's decision after each.

What is code

The liquidity gate. Every measured figure. Evidence grades. All of contract selection. Twenty-three checks. The readiness line. The checks on what the models write.

What is a language model

Six agent roles: an Evidence Retriever, three analysts, a Thesis agent and a Critic. They fetch, read, draft and argue. None of them sets a number or makes a decision.

What it keeps

Every decision, by the system or the user, in an append-only record. Every piece of evidence the agents cited. A trace of every model call, tool call and check.

What it will never do

Place or change an order: no tool can reach a broker. State a probability for a view. Call a candidate "recommended". Report a check as passed when the data was missing.

The path of one request

  1. The user picks a symbol. The web app opens a request and the workflow runs the gate, then pauses.
  2. The user continues. The workflow starts stage 2 on a background thread: measured figures, the Evidence Retriever, grades, three analysts in parallel, the Thesis agent with its validation check, the range-bound rule. The page shows each agent's status from the trace.
  3. The brief is shown and the workflow pauses. If there is a view, the request's pending records are committed to the permanent record at this point.
  4. The user accepts. Stage 3 fetches the chain and builds candidates in code, then pauses. Changing the ranking, the cost cap or the expiration re-runs it on the chain already fetched.
  5. The user selects a candidate. Stage 4 runs both checklists and the question in code, then the Evidence Retriever, then the Critic with its output check, then the readiness line, and pauses on the challenge.
  6. The user proceeds, returns to contracts, or stops. Whichever it is, the decision is recorded.

Each stage has its own time limit of 300 seconds. Spend stops at $1 a request and $10 a day.

The harness loop

run_agent in tradecraft/harness/runner.py does the whole job for every agent.

  1. Before the first call: build the system text (the agent's instructions, the rule that outside text is data, the required answer format) and offer only the tools the configuration names. A task larger than the input cap is not started.
  2. Each turn: check for Stop, the agent's time limit, the spend limits and the turn limit; then call the model. The model either asks for tools or gives an answer.
  3. A tool request is refused if the tool is not allowlisted, if the same call was already made, or if the tool-call limit is reached. Otherwise the tool runs, with one retry on an error and never past the agent's deadline. Text from an outside source is wrapped and labelled as data, and instruction-like text inside it is noted in the trace. A source that cannot supply its input becomes an "unavailable input" and the agent carries on.
  4. An answer is parsed into the agent's format and run through its output checks. If it fails, it is returned to the agent once with the reasons. If it fails again the run ends as "failed validation", keeping the rejected answer.
  5. Every step is traced: each model call with its token usage and cost, each tool call and result, each limit reached, each check. Each run records a fingerprint of its configuration, so an output can be traced to the prompt version that produced it.

A run ends in exactly one of: ok, failed validation, timed out, spend limit, model error, refused, cancelled, turn limit, input limit. The step that called it turns anything but "ok" into a stage stop with a plain message. A failure is never turned into a no view.

The workflow

One LangGraph StateGraph holds all four stages. LangGraph decides which node runs next; the harness decides what an agent may do inside a node.

  • Pauses are real stops. At a pause the graph saves its state and waits for the user's action. There are four stage pauses (gate, thesis, contracts, challenge) and two "stage stopped" pauses for stages 2 and 4.
  • A step never raises. A failure becomes a stage stop; later nodes of the stage pass through; the stopped pause offers what the design allows. Stage 2: Retry or Stop. Stage 4: Retry, "Continue with the checklists only", "Return to contracts", Stop. A retry re-runs only the nodes whose output is not already in the record, and is allowed once per stage.
  • One-time returns. The validation check and the Critic's output check run on the harness. The graph's validate and critic_check nodes only report the result, so an answer is never returned a second time.
  • Long stages run in the background. An action returns at once with running: true and the page polls. Stop sets a cancel signal that every agent checks before its next turn.
  • One open request at a time. A reload or a second tab shows the open request. If the engine restarts, the request is ended as "interrupted" and is not resumed.
  • Return to contracts clears stage 4's results, fetches the chain again and runs stage 4 anew for the new selection. The earlier challenge stays in the record.

The generated diagram of every node and edge is in docs/workflow-diagram.md.

Adding an agent

  1. Write its output format as a Pydantic model and its instructions as a string.
  2. Build an AgentConfig: a name, a role, the tools it may call, and its output checks. An output check is a function from the parsed answer to a list of plain sentences; an empty list passes.
  3. Add one line for it in config/limits.json (tool calls, seconds, output tokens) and one in config/models.json.
  4. Write a step that builds the task text, calls run_agent, and turns a result that is not "ok" into StepFailed. Wrap anything from an outside source with wrap_untrusted.
  5. Add a node for the step in workflow/graph.py. Put any check that may return the answer on the agent's configuration, not in the graph, so that it is returned once in total.

Adding a check to stage 4

  1. Write a function in stage4.py that takes the Case and returns check(id, result, detail, …) with one of the four results. Return "could not be checked" whenever an input is missing.
  2. Add its screen name to CHECK_NAMES and call it from run_checklists.
  3. If the Critic must not see it, leave it out in _for_critic.
  4. Add a test that strips its data and asserts it does not pass.

How the tests stand in for models

  • 373 tests, no key, no network. Run them with .venv/bin/python -m pytest -q.
  • Every agent runs on ScriptedModel, which returns prepared replies in order and records each request it was sent. A test can therefore assert both what the agent was shown and what happened to its answer.
  • The research index is a small fixed set of passages searched by keyword. The embedding model is never loaded in a test.
  • The workflow is tested on stand-in steps, so every pause, stage stop, retry and return is exercised without a model. Tests must not run the real stage 2 steps past the gate.
  • A test fails if a developer switch is left on in config/test_failures.json.
  • Live checks are separate and off by default: TRADECRAFT_LIVE=1 .venv/bin/python -m pytest -q tests/test_live.py -s.

What is not built

  • Stages 5 and 6: decision, sizing, the entry record and monitoring are not designed. After "Proceed to decision" the application shows one plain panel.
  • The Monitor. Nothing watches a thesis's invalidation criteria, so thesis check 8 stays flagged on every request and tells the user where to look.
  • A trace viewer. Traces are stored and can be read from the database; there is no screen for them.
  • Editing a drafted thesis, and the Records and Settings pages.
  • The range-bound brief and iron condors on screen. The rules and the engine exist; the screens were not designed for the demo.
  • A different model family for the Critic. That is the aim; for the demo both it and the Thesis agent run on Claude, and the challenge screen says so.
  • Data the free sources do not serve: the time of day of earnings, estimate revision history, quarterly consensus. The screens say "not available" and the affected checks say "could not be checked".

Challenge

Stage 4 tests the thesis and the selected contract before any money is committed. Fixed checks run first, in code. A critic agent then does the part that rules cannot. The stage reports what it finds in words and leaves the decision with the user.

1. Overview

By this point the system has drafted a view and proposed a contract for it. Both came from the same pipeline, so neither has yet been questioned. This stage questions them. It covers the thesis and, because stage 3 now proposes the contract, the choice of structure as well.

What the stage receives

The hand-off from stage 3: the selected candidate with its legs, quotes and measures; the thesis record with its complete evidence set and any horizon amendment; the candidates not selected; and how the choice was made, including the expiry, the filters, the priority and the ranking.

What the stage does not do

It does not change the thesis or the contract. It does not produce a score or a confidence figure. It does not set position size or place orders. In the version built first, it does not block a trade: it advises, and the user decides.

What the stage produces

ComponentDefinition
Thesis checksThe result of each fixed check on the thesis, passed or flagged, with the evidence item cited.
Contract checksThe result of each fixed check on the selected candidate, passed or flagged, with the figure that triggered it.
ObjectionsThe critic's objections, each with its basis in the retrieved evidence and its status.
The two casesThe strongest case for the thesis and the strongest case against it, written by the critic at the same length and shown side by side.
How the trade losesTwo or three specific paths to a loss for the selected structure.
ReadinessSet in code: whether anything the decision relies on has gone out of date. It is not a verdict on the trade.
User decisionProceed to stage 5, return to stage 3 to select another candidate, or stop.
  • Rules first, the critic second. Whatever can be checked by a fixed rule is checked in code. Instructing a model to be critical tends to produce the appearance of criticism, so the critic is confined to the judgements a rule cannot make.
  • Both sides, always. Evidence is retrieved for and against the thesis, and the critic must write the strongest case for it and the strongest case against it, at the same length. A one-sided challenge sways the reader without informing them.
  • Words, not a score. Objections are stated with their evidence. No rating and no confidence figure is shown.
  • Everything is recorded. Each check, each objection and the user's decision are written as decision records, including objections the user proceeds past.

2. The steps

The stage has six steps. Four are fixed rules in code and two are carried out by agents. The two checklists do not depend on each other and run at the same time; the remaining steps run in sequence.

1

Checklist on the thesis

CODE

Tests the thesis against fixed rules: whether it rests on a rejected signal, whether every finding it relies on carries a grade, whether it is contested or weakly supported, and whether the view runs against the base rate.

PURPOSE
Catch the faults a rule can catch, in the same way every time.
INPUT
The thesis record: the view, its basis, the evidence with grades, and the base rate.
OUTPUT
A list of thesis checks, each passed or flagged, with the evidence item cited.
2

Checklist on the contract

CODE

Tests the selected candidate against fixed rules: fit with the view, the expiry against any catalyst date, a poor-match expiry, the gap between the base-rate and market-implied chances, trading cost, and whether the structure sells premium.

PURPOSE
Challenge the choice of structure as well as the thesis.
INPUT
The selected candidate, the candidates not selected, the expiry, the priority and the ranking.
OUTPUT
A list of contract checks, each passed or flagged, with the figure that triggered it.
3

Restate the thesis as a question

CODE

Removes confident wording and first-person framing, and turns the claim into a neutral question.

PURPOSE
Prevent the critic from agreeing with a statement because it is asserted.
INPUT
The claim and basis of the thesis.
OUTPUT
The question the critic works on.
4

Retrieve evidence

AGENT · EVIDENCE RETRIEVER

Searches the research corpus for findings that support the question and findings that oppose it.

PURPOSE
Give the critic grounds from the project's own research, on both sides.
INPUT
The question from step 3 and the signals the thesis relies on.
OUTPUT
Supporting and opposing findings, each with its source and grade. Empty if nothing relevant is found.
5

Critique

AGENT · CRITIC

Identifies which claims the thesis depends on, a rejected signal presented under another name, and claims that do not fit together. Writes the strongest case for the thesis.

PURPOSE
Carry out the judgement that rules cannot.
INPUT
The question, the retrieved findings and the results of both checklists.
OUTPUT
Objections, each with its basis and status, and the strongest case for the thesis.
6

Present and record

CODE

Shows one challenge screen and takes the user's decision.

PURPOSE
Put the challenge before the user ahead of any sizing, and keep it on file.
INPUT
The outputs of steps 1, 2 and 5.
OUTPUT
The challenge screen, and decision records for every objection and for the user's choice: proceed, return to stage 3, or stop.
  • What passes to stage 5. The selected candidate and the thesis, unchanged, with the full list of flags and objections attached.
  • If the user returns to stage 3, the challenge is kept on record and runs again on the newly selected candidate.

3. Checks on the thesis

Step 1 runs twelve fixed checks on the thesis. Each reads fields that the earlier stages have already recorded. None involves a model.

Four possible results

PASSED

The check ran and found nothing.

FLAGGED

The check found something. The item that triggered it is cited.

NOT APPLICABLE

The check does not apply to this view or instrument.

COULD NOT BE CHECKED

The data was missing. Shown as plainly as a flag.

  • A check never reports "passed" for want of data. Missing data gives "could not be checked".
  • A flag does not block. It is put before the user and passed to the critic.
  • Checks that would be flagged on every request are left out, since a flag that is always raised says nothing. Check 8 is the one stated exception.

5. The question and the evidence

Steps 3 and 4 prepare what the critic works from: a neutral question in place of the thesis as written, and passages from the project's research on both sides of it.

Restating the thesis as a question

EXPLANATION ONLYAs a user might write it

"I'm confident this is going higher. Guidance was clearly raised and estimates keep climbing, so it's an easy 30-day call."

EXPLANATION ONLYAs the critic receives it

Do the following support a close above the reference price for EXMP at 30 days?

  1. Guidance was raised at the latest report.
  2. Consensus estimates rose 3% over the last 30 days.
  • A fixed template in code. No model is involved. The direction, the horizon and each claim were already separated in stage 2, and the template assembles them.
  • Withheld from the critic: the original wording, the written basis, and who wrote the thesis. A model tends to agree with a confident statement, and more so when it is presented as someone's own belief.
  • Nothing is lost. The original text stays in the record and on the user's screen.

Retrieving evidence

Evidence from stage 2Evidence retrieved in this stage
AboutThis company: its filings, results and guidance.Whether this kind of reasoning has worked.
Example"Guidance was raised on 3 November.""Is a guidance raise followed by a higher price, and for how long?"
SourceCompany filings and market data.The project's research reports, specification and decision records.
  • The project's research only. The web is not searched. The research already records what was found and how strong it was.
  • Each topic is searched both ways: for findings that the reasoning has worked, and for findings that it has not. There is one topic per claim and one for the type of structure selected.
  • A relevance bar, and a cap. A passage that does not clearly bear on the topic is dropped. At most three passages per side per topic.
  • One retry. A search that returns nothing is reworded once, then reported as "nothing found".
  • No conclusion. The retriever returns passages with their sources. It does not say which side is stronger.

6. The critic

Step 5 is the one step that needs judgement. The critic receives the question, the retrieved passages and the results of both checklists. It does not see the original wording and is not told who wrote the thesis.

Nine tasks

#TaskWhat keeps it grounded
1Find what the thesis depends onNames the claim whose removal would leave nothing.
2Spot a rejected signal in other wordsCites the claim and the entry on the rejected-signal list.
3Find claims that do not fit togetherCites the claims.
4Read the two checklists togetherCites the checks that are one problem.
5Write the strongest case for the thesisRequired in every run.
6Priced-in testCode supplies the price move since each finding became public. The critic interprets a figure and does not guess.
7Write the strongest case againstBuilt only from recorded opposing evidence, the base rate, the flags and the retrieved passages. The same length as the case for.
8How this trade losesTwo or three specific paths, each citing a check or a finding.
9What is missingLimited to what stage 2 recorded as unavailable or not found. The critic may not invent a gap.

Rules

What the critic must do

Cite the grounds for every objection: a check, a claim or a retrieved passage. State for every claim whether it holds, holds only in a narrower form, or does not hold. Write both cases at the same length.

What the critic may not do

Give a verdict, a score or a confidence figure. Advise whether to trade. Raise more than five objections. Name a gap or a fact that is not in the record or the retrieved passages.

  • The critic may concede. With clean checks and nothing found against, the right output is the two cases and few or no objections.
  • The critic's output is checked in code before the user sees it. Every citation must exist, every claim must have a standing, both cases must be present, and the cap must be respected. An output that fails is returned once. If it fails again, the screen shows the two checklists and states that the critic's output was rejected.
  • Model. In the first version the critic runs on the same model family as the agent that drafted the thesis, and the screen says so. Two instances of one model tend to share blind spots, so a different family remains the aim.
  • Limits. The critic does no new research. If stage 2 did not find adverse news, the critic will not find it either.

The readiness line

The critic gives no go or no-go. The readiness line is set by code from the checks. It concerns whether the inputs to the decision are still valid, and says nothing about whether the trade is a good one.

ReadinessWhenWhat the screen suggests
NOT READYThe thesis is stale; the contract's price has moved by more than its trading cost since selection; a range-bound view's invalidation condition has been met; or the critic's output was rejected.The specific remedy: run stage 2 again, or return to stage 3.
READY with itemsNone of those, and at least one check is flagged or could not be checked."No blocking conditions", with the number of items for the user's judgement.
READYNone of those, and nothing flagged."No blocking conditions."
  • Validity, not merit. "Not ready" means something the decision relies on has gone out of date.
  • Flags are not counted into a rating. Six flagged items do not make a trade worse than two; that depends on which they are.
  • It does not block. The user may proceed past "not ready", and that is recorded.
  • "Could not be checked" is shown with the flags, never with the passes. Passed checks are collapsed into one line.

What is handed to stage 5

  • The thesis and the selected contract, unchanged.
  • The full list of flags and objections, including any the user proceeded past.
  • Three results that stage 5 uses directly: risk flags and events, which reduce size; invalidation that cannot be watched, which makes the price-based exit matter more; and the volatility state.
  • If the user returns to stage 3, this challenge is kept on record and a new one runs on the newly selected candidate.

Scope of the first version. The challenge advises and does not block. The critic's power to block a trade, the structured override, and the test of the critic's own accuracy on planted theses are designed in outline and are not part of the first version.

Known data gaps. Earnings dates and ex-dividend dates have no data source. Until one is chosen, thesis check 6 and contract check 8 report those parts as "could not be checked".

Provisional values. The same-day rule in thesis check 2, the two thresholds in thesis check 11, and the 1.25 threshold in contract check 5 are design choices.

Implementation status. This page documents the design. The stage is not yet implemented.
